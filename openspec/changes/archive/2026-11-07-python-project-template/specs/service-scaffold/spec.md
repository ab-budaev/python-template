# Spec Delta

## Purpose

Даёт сгенерированному проекту работающий каркас HTTP-сервиса: приложение с health-проверкой, конфигурация из окружения, логирование, телеметрия, тесты и инструменты качества — чтобы разработка начиналась с бизнес-логики, а не с инфраструктурной настройки.

## ADDED Requirements

### Requirement: Health-проверка сервиса

Приложение ДОЛЖНО (MUST) предоставлять endpoint `GET /health`, возвращающий HTTP 200 и JSON-ответ `{"status": "ok"}`. Endpoint ДОЛЖЕН (MUST) быть доступен без аутентификации и использоваться для liveness/readiness-проб.

#### Scenario: [P0] Проверка здоровья работающего сервиса

- **GIVEN** сервис запущен
- **WHEN** клиент выполняет `GET /health`
- **THEN** ответ имеет статус 200 и тело `{"status": "ok"}`

#### Scenario: [P0] Endpoint не требует аутентификации

- **GIVEN** сервис запущен
- **WHEN** клиент выполняет `GET /health` без учётных данных
- **THEN** ответ не содержит ошибки авторизации

### Requirement: Конфигурация через переменные окружения

Приложение ДОЛЖНО (MUST) получать настройки из переменных окружения (с поддержкой файла `.env`): имя приложения, окружение, режим отладки, уровень логирования. Имя приложения по умолчанию ДОЛЖНО (MUST) совпадать с именем проекта. Пользователь ДОЛЖЕН (MUST) иметь возможность расширить настройки собственными полями через наследование.

#### Scenario: [P0] Настройки читаются из окружения

- **GIVEN** переменная окружения `APP_ENV` установлена в `staging`
- **WHEN** приложение запускается
- **THEN** внутри приложения значение окружения равно `staging`

#### Scenario: [P0] Значения по умолчанию без окружения

- **GIVEN** переменные окружения не заданы и файл `.env` отсутствует
- **WHEN** приложение запускается
- **THEN** приложение стартует с окружением `local`, отладкой выключенной и уровнем логирования по умолчанию

#### Scenario: [P1] Расширение настроек пользователем

- **GIVEN** пользователь объявил наследника базовых настроек с собственным полем
- **WHEN** приложение запускается с этими настройками
- **THEN** приложение стартует, а значение собственного поля доступно внутри приложения

### Requirement: Структурное логирование

Приложение ДОЛЖНО (MUST) вести логи через единый интерфейс: при включённой отладке — человекочитаемый формат с цветами, при выключенной — структурированный JSON с уровнем, временем и именем события. Настройки логирования ДОЛЖНЫ (MUST) применяться из конфигурации приложения (уровень, режим отладки).

#### Scenario: [P1] Читаемые логи в режиме отладки

- **GIVEN** приложение запущено с включённой отладкой
- **WHEN** приложение логирует событие
- **THEN** событие выводится в консоль в читаемом формате

#### Scenario: [P0] Структурированные логи в рабочем режиме

- **GIVEN** приложение запущено без отладки
- **WHEN** приложение логирует событие
- **THEN** событие выводится в JSON-формате, пригодном для машинного разбора

### Requirement: Опциональная телеметрия

Приложение ДОЛЖНО (MUST) поддерживать экспорт телеметрии (трейсы HTTP-запросов и логи) через OTLP; экспорт управляется стандартными переменными окружения OpenTelemetry и по умолчанию отключён для локальной разработки.

#### Scenario: [P2] Телеметрия отключена по умолчанию

- **GIVEN** приложение запущено без переменных OpenTelemetry
- **WHEN** обрабатываются HTTP-запросы
- **THEN** приложение работает без экспорта телеметрии и не падает при отсутствии коллектора

#### Scenario: [P1] Экспорт при явной настройке

- **GIVEN** задан endpoint OTLP-коллектора и телеметрия явно включена
- **WHEN** обрабатываются HTTP-запросы
- **THEN** трейсы запросов и логи экспортируются в указанный коллектор

### Requirement: Тестовый каркас

Сгенерированный проект ДОЛЖЕН (MUST) содержать тесты на health-endpoint и фикстуры для HTTP-клиента тестирования, запускаемые одной командой. Тесты ДОЛЖНЫ (MUST) проходить без внешних зависимостей (сеть, БД, коллектор телеметрии).

#### Scenario: [P0] Прогон тестов из коробки

- **GIVEN** проект только сгенерирован, зависимости установлены
- **WHEN** пользователь запускает команду тестов
- **THEN** все тесты проходят успешно без внешних сервисов

### Requirement: Контроль качества кода

Проект ДОЛЖЕН (MUST) включать настроенные линтер и строгую проверку типов, а также единую команду их запуска. Стандартная кодовая база шаблона ДОЛЖНА (MUST) проходить обе проверки без ошибок.

#### Scenario: [P0] Проверка качества из коробки

- **GIVEN** проект только сгенерирован, зависимости установлены
- **WHEN** пользователь запускает команду проверки качества
- **THEN** линтер и проверка типов завершаются без ошибок

### Requirement: Контейнерная сборка

Проект ДОЛЖЕН (MUST) включать multi-stage Dockerfile: dev-слой для разработки, builder для установки зависимостей, release-образ, запускаемый непривилегированным пользователем и поднимающий HTTP-сервер через entrypoint.

#### Scenario: [P1] Сборка release-образа

- **GIVEN** проект сгенерирован
- **WHEN** пользователь собирает release-образ и запускает контейнер
- **THEN** сервер поднимается внутри контейнера и отвечает на `GET /health` кодом 200

#### Scenario: [P2] Контейнер не запускается от root

- **GIVEN** release-образ собран
- **WHEN** контейнер запущен
- **THEN** процесс сервера выполняется под непривилегированным пользователем

### Requirement: Локальная разработка в контейнере

Проект ДОЛЖЕН (MUST) включать конфигурацию dev-контейнера, в котором зависимости установлены, исходный код смонтирован и доступны отладка сервера и запуск тестов; порт сервера проброшен наружу.

#### Scenario: [P2] Открытие проекта в dev-контейнере

- **GIVEN** проект сгенерирован и открыт в редакторе с поддержкой dev-контейнеров
- **WHEN** разработчик открывает проект в dev-контейнере
- **THEN** среда готова к работе без ручной установки зависимостей, сервер и тесты запускаются из редактора

### Requirement: Локальный запуск через compose

Проект ДОЛЖЕН (MUST) включать compose-файл, поднимающий сервис одной командой с проброшенным портом HTTP-сервера и загрузкой переменных из `.env`.

#### Scenario: [P1] Запуск сервиса через compose

- **GIVEN** проект сгенерирован, Docker-демон запущен
- **WHEN** пользователь выполняет команду подъёма compose-сервиса
- **THEN** сервер доступен на порту хоста и отвечает на `GET /health`
